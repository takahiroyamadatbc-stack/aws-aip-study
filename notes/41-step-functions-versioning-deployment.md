# AWS Step Functions のバージョン・エイリアスと段階的デプロイ

## これは何か

**AWS Step Functions**のステートマシンには、Lambda関数と同じ発想の**バージョン（Version）**と**エイリアス（Alias）**という仕組みがある。これを使うと、ステートマシンの定義を新しい内容に更新する際に、**一度に100%切り替えるのではなく、新旧バージョンへのトラフィックを段階的に配分しながら移行する**（gradual/canary/linearデプロイ）ことができる。

GenAIエージェントのオーケストレーション（Bedrock Agentsの裏側やStrands Agentsのワークフロー実行など、[[23-bedrock-agentcore]] [[24-strands-agents-sdk]]参照）をStep Functionsで組んでいる場合、ワークフロー定義を更新するたびに全トラフィックがいきなり新定義に切り替わると、不具合があったときの影響範囲が大きい。バージョン・エイリアス機能はこの「デプロイ時のリスク」を小さくするための機能。

## 登場する要素

- **バージョン（Version）**: ステートマシンの定義を発行（publish）した時点のスナップショット。発行後は**不変（immutable）**。`stateMachineArn:1`のように末尾に番号が付いたARNで参照する
- **エイリアス（Alias）**: 1つ以上のバージョンに**重み付け（weight）**してトラフィックを振り分けるポインタ。`stateMachineArn:my-alias`のような固定ARNを持ち、呼び出し側（EventBridge、他のStep Functions、Lambda等）はこのエイリアスARNを実行対象として指定しておけば、裏側のバージョン切り替えを意識しなくてよい
- **RoutingConfiguration**: エイリアスにぶら下がるバージョンとその重み（%）の組み合わせ。これを時間経過とともに書き換えていくことで段階的デプロイを実現する

## デプロイタイプ（RoutingConfigurationの更新パターン）

CloudFormationでは `AWS::StepFunctions::StateMachineAlias` の `DeploymentPreference` プロパティで指定する。CLI/CDK/コンソールからも同様に設定可能。

| デプロイタイプ | 挙動 |
|---|---|
| **ALL_AT_ONCE** | エイリアス更新と同時に100%を新バージョンへ即時切り替え |
| **LINEAR** | 指定した%を、指定した分間隔で段階的に増やしていく。例: 増分20%・間隔600分 → 600分ごとに20%ずつ増え、5回（3000分）で100%に到達 |
| **CANARY** | まず少量（例10%）を新バージョンに投入し、指定した秒数のあいだ様子を見る。その間隔内に問題が起きなければ、残り（例90%）を一気に新バージョンへ切り替える。増分は最初と最後の2段階のみ |

- いずれの方式でも、**CloudWatchアラーム**を関連付けておくと、移行途中にアラームが発火した場合は**自動的にロールバック**（トラフィックを旧バージョン100%へ戻す）される
- 呼び出し元は常にエイリアスARNを指定するだけでよく、**どのバージョンにどれだけ流れているかを呼び出し元が意識する必要はない**

## 他サービスの類似機能との違い（混同しやすいポイント）

「段階的なトラフィック配分」自体は複数のAWSサービスに存在するが、**担当するレイヤーと設定方法がサービスごとに異なる**。

| サービス | 段階的トラフィック配分の実体 |
|---|---|
| **Step Functions** | ステートマシンの**バージョン＋エイリアス＋RoutingConfiguration**（Step Functions自身が完結して持つ機能） |
| **Lambda関数** | Lambdaの**エイリアス**に対する**AWS CodeDeploy**のデプロイ設定（`Canary10Percent5Minutes`等）。Lambda単体ではなくCodeDeployが実体 |
| **SageMakerエンドポイント** | **プロダクションバリアント（Production Variant）**の重み（`InitialVariantWeight`）を段階的に書き換える、または組み込みの段階的ロールアウト機能を使う |
| **API Gateway** | ステージの**カナリアリリース（Canary Release）**設定 |
| **ECS/CodeDeploy(Blue/Green)** | ALBのターゲットグループ間でのLinear/Canaryトラフィックシフト |

Step Functionsの場合、**CodeDeployを別途経由する必要がなく、Step Functions自身のリソース（バージョン・エイリアス）だけで完結する**のが最大の特徴。Lambdaの段階的デプロイ＝CodeDeployという連想で「Step FunctionsもCodeDeploy経由のはず」と誤解しないこと。

## 試験でのひっかけポイント整理

- 「Step Functionsのステートマシン定義自体にトラフィック配分の機能はなく、外部サービス（CodeDeploy等）が必要」→ 誤り。**バージョンとエイリアス**というStep Functions自身の機能で完結する
- 「LINEARとCANARYの違い」→ LINEARは**一定間隔で段階的に**増分、CANARYは**最初の少量出し＋様子見後に残り一気に**の2段階。刻み方が違う
- 「デプロイ中に問題が起きても手動でロールバックするしかない」→ 誤り。**CloudWatchアラーム**と連携させれば自動ロールバックできる
- 「新バージョンを発行すると、呼び出し元のARNも書き換える必要がある」→ 誤り。呼び出し元は**エイリアスARN**を固定で指定しておけばよく、バージョン切り替えはエイリアス側のRoutingConfiguration更新だけで完結する
- 「発行済みのバージョンは後から定義を書き換えられる」→ 誤り。バージョンは**発行時点のスナップショットで不変**。定義を変えたい場合は新しいバージョンを発行する
