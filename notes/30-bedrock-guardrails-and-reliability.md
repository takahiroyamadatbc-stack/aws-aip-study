# Amazon Bedrock Guardrails と、生成AIの信頼性を高めるその他の手段

生成AIアプリケーションを安全・確実に運用するには、「モデルに悪いことを言わせない／させない」という**ガードレール（防御）**の観点と、「モデルの出力を事実に基づいた正しいものにする」という**グラウンディング（根拠付け）**の観点の両方が要る。前者の主役がBedrock Guardrailsで、後者はGuardrailsの一部機能（Contextual Grounding Check）に加えて、アプリケーション設計側で補う手段（構造化出力、類似度検証、多重生成）が存在する。このノートはBedrock Guardrailsの各フィルタ機能と、それを含めた**多層防御**という考え方、そしてGuardrails単体に頼らない信頼性向上手段を整理する。

## Bedrock Guardrails のフィルタ機能

Guardrailsは、モデルに依存しない**独立したポリシーセット**として作成し、複数のモデル・複数のアプリケーションから使い回せる。プロンプト（入力）とモデル応答（出力）の両方に適用でき、ポリシーごとに入力/出力それぞれで有効化するかを選べる。

| ポリシー | 検知対象 | 設定の仕方 | 主な用途 |
|----------|----------|------------|----------|
| コンテンツフィルター（Content filters） | ヘイト、侮辱、性的、暴力、不正行為（Misconduct）、プロンプトアタック（Prompt Injection/Jailbreak） | カテゴリごとに強度を `なし/低/中/高` で設定 | 有害コンテンツの生成・誘導の一般的な抑止 |
| 拒否トピック（Denied topics） | 自然言語で定義した「話してほしくない話題」（例: 「投資助言」「競合他社の批判」） | トピック名＋説明文＋任意でサンプル文言を登録 | 業務ドメイン固有のコンプライアンス制約（金融助言の禁止等） |
| ワードフィルター（Word filters） | 特定の単語・フレーズ（カスタム辞書）、および組み込みの冒涜表現リスト | NGワードリストを登録 | ブランド固有の禁句、競合製品名、内部コードネーム等の遮断 |
| 機微情報フィルター（Sensitive information filters） | PII（氏名、メール、電話番号、クレジットカード番号等の組み込みエンティティ）、正規表現で定義するカスタムエンティティ | エンティティ種別ごとに「ブロック」または「マスキング（redact）」を選択 | 個人情報の入力遮断・出力からの自動マスキング |
| コンテキストグラウンディングチェック（Contextual grounding check） | 応答が**参照ソース（RAG検索結果等）に根拠付けられているか**（Grounding）／**ユーザーの質問に関連しているか**（Relevance） | Grounding score / Relevance score のしきい値（0〜1）を設定 | ハルシネーション（幻覚）の検知・抑制（詳細は後述） |
| Automated Reasoning checks | 形式論理（数学的に検証可能なルール）と照らして応答の論理的な正しさを検証 | ドメイン固有のルールをAutomated Reasoningポリシーとして定義 | 数値計算・ポリシー適用など「正解が一意に決まる」業務ロジックの検証 |

```bash
# Guardrailの作成例（コンテンツフィルター + 拒否トピック + PIIマスキングの一部を抜粋）
aws bedrock create-guardrail \
  --name aip-study-sample-guardrail \
  --content-policy-config '{
    "filtersConfig": [
      {"type": "VIOLENCE", "inputStrength": "HIGH", "outputStrength": "HIGH"},
      {"type": "PROMPT_ATTACK", "inputStrength": "HIGH", "outputStrength": "NONE"}
    ]
  }' \
  --sensitive-information-policy-config '{
    "piiEntitiesConfig": [
      {"type": "EMAIL", "action": "ANONYMIZE"},
      {"type": "US_SOCIAL_SECURITY_NUMBER", "action": "BLOCK"}
    ]
  }' \
  --blocked-input-messaging "その入力は処理できません" \
  --blocked-outputs-messaging "その回答は提供できません" \
  --tags Key=Project,Value=aip-study

# 作成済みGuardrailは、モデル呼び出しとは独立に単体でテストできる（ApplyGuardrail API）
aws bedrock-runtime apply-guardrail \
  --guardrail-identifier <GUARDRAIL_ID> \
  --guardrail-version DRAFT \
  --source INPUT \
  --content '[{"text": {"text": "テストしたい入力テキスト"}}]'
```

- Guardrailは`Converse`/`InvokeModel`呼び出し時に`guardrailConfig`として指定する他、**Knowledge Bases・Agents・カスタムアプリケーション（`ApplyGuardrail` API単体）**からも共通で利用できる。「モデル呼び出しと常にセットでしか使えない」わけではない点に注意
- `PROMPT_ATTACK`フィルターは**入力側のみ**に意味がある（出力そのものがプロンプトアタックになることはない）。表の`outputStrength: NONE`はこの非対称性を示す例
- PIIフィルターの`action`は`BLOCK`（該当した時点でリクエスト/レスポンス全体を拒否）と`ANONYMIZE`（該当箇所だけを`{EMAIL}`のような形にマスキングして処理継続）を選べる。**業務上そのまま処理を続けたいならANONYMIZE、機微情報の混入自体を防ぎたいならBLOCK**という使い分け

## Guardrailsのティア（Standard / Classic）

これは何か: Bedrock Guardrailsには**Standard**と**Classic**という2つの「ティア（tier）」があり、Guardrail作成時にどちらの実装・検出エンジンを使うかを選択する。ティアはGuardrail全体に対する設定であり、フィルタ機能そのものとは別軸のパラメータ。Classicは元々提供されていた実装で、Standardはより新しく機能強化された実装という位置づけ（新規に作るGuardrailはAWSもStandardを推奨している）。

| 観点 | Standardティア | Classicティア |
|------|-----------------|------------------|
| 対応言語 | 多言語対応が強化されている | 英語・フランス語・スペイン語に特化した確立済みの機能 |
| リージョン | クロスリージョン推論に対応 | — |
| コード内の有害コンテンツ検出 | 強化されている | 標準的な対応 |
| **プロンプトリーケージ検出** | **サポートされる** | **サポートされない**（明示的に対応外） |
| 全体的な検出精度 | より堅牢なパフォーマンス | Standardと比べると相対的に見劣りする |

- 「プロンプトアタック（インジェクション・ジェイルブレイク）を検出したい」だけならどちらのティアでも`PROMPT_ATTACK`フィルターは機能する。しかし**プロンプトリーケージ（システムプロンプトの内容を引き出そうとする攻撃）の検出はStandardティア限定の機能**であり、ここがClassicティアとの決定的な差になる
- 試験でも「Classicティア＋プロンプト攻撃フィルター」という一見もっともらしい構成が誤答選択肢として登場しやすい。プロンプトリーケージ要件が問題文に含まれているかどうかを見て、含まれていればStandardティア必須と判断する

## InvokeModel APIでのプロンプト攻撃フィルタリング — XMLタグ付けが必須

Guardrailsの`PROMPT_ATTACK`フィルターは、モデルに渡すプロンプトの中で「どこがシステムプロンプト（開発者の指示）で、どこがユーザー入力か」を区別できて初めて機能する。この区別の仕組みがAPIによって異なる点に注意。

| API | ユーザー入力の識別方法 |
|-----|--------------------------|
| `Converse` / `ConverseStream` | APIのメッセージ構造（`role: user`等）自体がシステムプロンプトとユーザー入力を分離しているため、追加の対応は不要 |
| `InvokeModel` / `InvokeModelWithResponseStream` | プロンプト全体が1つのテキストとしてモデルに渡る構造のため、**ユーザー入力部分を所定のXMLタグで明示的に囲む**必要がある。タグを付けないと`PROMPT_ATTACK`フィルターが機能しない |

```text
<amazon-bedrock-guardrails-guardContent_{ランダムなsuffix}>
ここにユーザーが送信した入力をそのまま挿入する
</amazon-bedrock-guardrails-guardContent_{ランダムなsuffix}>
```

- タグ名の`{suffix}`部分は**リクエストごとにランダムな文字列を生成して使う**ことが推奨されている。固定のタグ名を使ってしまうと、悪意あるユーザーが「`</amazon-bedrock-guardrails-guardContent_固定値>`のような文字列を自分の入力に含めてタグを閉じ、後続をシステムプロンプト側として注入する」という攻撃が成立してしまうため
- つまり、InvokeModel系APIでGuardrailsのプロンプト攻撃対策を有効にするには、①Guardrailの設定（ティア・フィルタ強度）に加えて、②呼び出し側アプリケーションでのXMLタグ付け実装、の**両方が必要**。Guardrailを作成しただけでは不十分という点が見落としやすい

## PII検出の使い分け：Comprehend / Macie / Guardrails

「PIIを検出する」と一口に言っても、**何に対して**（リアルタイムのテキストか、S3に溜まった保存データか）、**何のために**（生成AIパイプラインへの混入防止か、データレイク全体の棚卸しか）で使うべきサービスが変わる。試験では3つのサービスの役割の違いを問う形で出やすい。

| サービス | 検出対象データ | 仕組み | 主なユースケース | 検出後のアクション |
| --- | --- | --- | --- | --- |
| **Amazon Comprehend** | 任意のテキスト（アプリから渡す文字列。リアルタイム同期API、または大量ドキュメントの非同期バッチジョブ） | 事前学習済みNLPモデルによるPIIエンティティ検出。組み込みエンティティ（氏名、住所、クレジットカード番号、SSN等）に加え、ラベル付きデータで**カスタムエンティティ認識器**を学習させることも可能 | 生成AI・Bedrockに限らない汎用のテキスト分析パイプラインで、任意の箇所にPII検出・マスキングを組み込みたい場合（例: Bedrock以外のモデルを使うアプリの前処理／ログ出力前のマスキング） | `ContainsPiiEntities`（有無の真偽のみ）、`DetectPiiEntities`（エンティティ種別・位置・信頼度スコアの一覧）、リダクション機能でマスキング済みテキスト（`RedactedText`）を取得することも可能 |
| **Amazon Macie** | **S3バケットに保存されているオブジェクト**（ドキュメント、CSV、ログ等の保存データ＝at rest） | 機械学習とパターンマッチングを組み合わせて、S3内のオブジェクトを横断的にスキャンし、PIIや資格情報・財務情報などの機微データを発見 | データレイク・S3バケット全体を対象にした「どこに個人情報が眠っているか」の可視化、GDPR等コンプライアンス対応のためのデータ棚卸し・継続的モニタリング | Findingsとして検出結果（バケット名、オブジェクト、検出された機微データの種類・件数等）を出力。Security Hubと統合してセキュリティ運用の一部に組み込める |
| **Bedrock Guardrails（機微情報フィルター）** | **Bedrockモデル呼び出しの入力・出力テキスト**（プロンプトとレスポンス。リアルタイム） | 組み込みPIIエンティティ＋正規表現で定義するカスタムエンティティ（本ノート前半の表を参照） | 生成AIアプリケーションにおいて、ユーザー入力やモデル出力にPIIが混入するのをその場で防ぎたい場合 | エンティティ種別ごとに`BLOCK`（該当時にリクエスト/レスポンス全体を拒否）または`ANONYMIZE`（該当箇所だけをマスキングして処理継続）を選択 |

- **対象データの違いが最大の分岐点**。「S3に置いてあるファイル群からPIIを見つけたい」→Macie、「今まさにモデルとやり取りしているテキストからPIIを見つけたい」→Comprehend（汎用）またはGuardrails（Bedrock限定）
- **ComprehendとGuardrailsの違い**は「汎用NLP API（自分でどこに組み込むか設計する）」か「Bedrockのモデル呼び出しパイプラインに標準で統合済みのフィルタ」かの違い。Bedrockモデルを使っていてPII対策をしたいだけなら、素直にGuardrailsを使う方が実装コストが低い。Comprehendが必要になるのは、Bedrock以外のモデル・パイプラインを使っている場合や、S3ドキュメントの一括処理・カスタムエンティティ認識のように、Guardrailsの守備範囲外の要件がある場合
- MacieはS3という**特定のデータストア**に特化したサービスであり、APIを介してリアルタイムに渡されたテキスト（例: ユーザーがチャットに入力した文字列）をその場で検査する用途には使えない（そもそもそのようなリアルタイム呼び出しAPIを持たない）
- 3つを組み合わせる構成も現実的: Macieで既存のS3データレイクの機微情報を棚卸しし、Comprehendでバッチ処理・カスタムパイプラインのPII検出を行い、Bedrockアプリの入出力はGuardrailsで防御する、という**層ごとに適材適所で使い分ける**設計

## 多層防御（Defense in Depth）としてのGuardrails

試験・実務の両方でよく問われる誤解は「Guardrailsを設定すれば安全性は担保される」という考え方。Guardrailsはあくまで**フィルタ層の1つ**であり、単体で100%の防御を保証するものではない（強度を`高`にしても検知漏れ・過検知は起こり得る）。実務では以下のような複数層を重ねる。

| 層 | 具体例 | 役割 |
|----|--------|------|
| 入力検証（アプリ層） | APIレベルでのスキーマ検証、文字数制限、既知の攻撃パターンの事前フィルタ | Guardrailsに届く前の粗い足切り |
| プロンプトエンジニアリング | システムプロンプトで役割・禁止事項を明示、Few-shotで望ましい拒否応答の型を与える | モデル自身の応答方針をそもそも安全な方向に誘導 |
| Bedrock Guardrails | 本ノート前半の各フィルタ | モデル・プロンプトに依存しない一貫したポリシー適用 |
| 出力後処理（アプリ層） | 出力のスキーマ検証、危険なアクション（決済・削除等）実行前の追加チェック | Guardrailsをすり抜けた場合の最終防波堤 |
| IAM／ネットワーク境界 | Bedrockモデル呼び出し権限の最小化、VPCエンドポイント、ログ（CloudTrail）による監査 | モデル出力の中身とは別軸の、アクセス制御としての防御 |
| 人間によるレビュー（Human-in-the-loop） | 高リスクなアクション（送金・契約締結等）は自動実行せず人間の承認を挟む | モデルの誤りが実害に直結する場面での最終的なセーフティネット |

- 多層防御の要点は「**どの層も単独では信頼しない**」こと。Guardrailsが強力だからといってプロンプトエンジニアリングや出力検証を省略してよい、という設計は誤り
- 各層は独立してテスト・更新できることが望ましい（Guardrailsはモデルやプロンプトを変更しなくても`ApplyGuardrail`単体で検証・改訂できる、というのがBedrock Guardrailsを独立ポリシーとして設計している理由の1つ）

## Grounding（ハルシネーション抑制）

**ハルシネーション**とは、モデルが「もっともらしいが事実に基づかない（根拠のない）」内容を生成してしまう現象。RAGのように外部ソースを検索して回答させる構成でも、モデルが検索結果を無視・拡大解釈して事実と異なる内容を答えてしまうことがある。

Bedrock Guardrailsの**Contextual Grounding Check**は、この問題に対する組み込みの検知機構。

- **Grounding score**: モデルの応答が、渡された参照ソース（grounding source。RAGの検索結果チャンクなど）にどれだけ根拠付けられているかのスコア（0〜1）。低いほど「ソースにない内容を答えている＝ハルシネーションの疑い」
- **Relevance score**: モデルの応答が、ユーザーの質問にどれだけ関連しているかのスコア（0〜1）。低いほど「質問とかみ合っていない／脱線した回答」
- 両スコアそれぞれにしきい値を設定でき、しきい値を下回った応答はブロック（あるいは事前定義のメッセージに差し替え）される
- 内部的には自然言語推論（NLI）に近いアプローチで、参照ソースと応答の間の**含意関係**を評価している（キーワード一致のような単純な文字列比較ではない）

```python
import boto3

client = boto3.client("bedrock-runtime")

response = client.converse(
    modelId="anthropic.claude-3-5-sonnet-20241022-v2:0",
    messages=[{"role": "user", "content": [{"text": "先月の売上は？"}]}],
    guardrailConfig={
        "guardrailIdentifier": "<GUARDRAIL_ID>",
        "guardrailVersion": "1",
        "trace": "enabled",
    },
    # grounding sourceはKnowledge Baseの検索結果や、
    # 自前で取得したドキュメントをプロンプト中に埋め込む形で渡す
)
```

- Contextual Grounding Checkは**RAG構成（検索結果というソースが存在する場合）に特化した機能**であり、ソースなしの自由生成（雑談等）には適用対象がない点に注意
- 「Grounding score」と「Relevance score」は評価軸が異なる。**根拠はあるが質問には答えていない**（Grounding高・Relevance低）応答と、**質問には答えているが根拠がない**（Grounding低・Relevance高）応答は別の問題として検知される

## その他の信頼性向上手段

Guardrailsのフィルタ・グラウンディングチェックだけでなく、アプリケーション設計側で信頼性（正確性・再現性）を高める手段がいくつかある。試験では「Guardrails以外にどんな手段があるか」を問う形で出やすい。

### 構造化出力による決定性の確保

自由記述のテキスト生成は表現の揺らぎや形式崩れが起きやすい。**出力形式そのものを固定する**ことで、後続処理での解釈ミスやハルシネーションの余地を減らせる。

| 手段 | 概要 | 効果 |
|------|------|------|
| JSON Schema（Tool useの強制） | Converse APIの`toolConfig`で応答スキーマをツール定義として与え、`toolChoice`でそのツールの呼び出しを強制する | モデルの出力を決まったキー・型のJSONに固定でき、パースエラーや自由記述由来の揺らぎを防げる |
| Text-to-SQL | 「質問に直接答えさせる」のではなく、モデルには**SQLクエリを生成させるだけ**にし、実際の数値・事実はDBへのクエリ実行結果から取得する | 「先月の売上は？」のような数値を伴う質問で、モデルが数値そのものを生成しない（＝ハルシネーションしようがない）構成にできる。正しさの担保はSQLの妥当性検証に一本化される |

```python
# JSON Schemaで出力形式を強制する例（Converse APIのtoolConfig）
tool_config = {
    "tools": [{
        "toolSpec": {
            "name": "extract_order_info",
            "description": "注文情報を抽出する",
            "inputSchema": {
                "json": {
                    "type": "object",
                    "properties": {
                        "order_id": {"type": "string"},
                        "amount": {"type": "number"},
                        "status": {"type": "string", "enum": ["pending", "shipped", "cancelled"]},
                    },
                    "required": ["order_id", "amount", "status"],
                }
            },
        }
    }],
    "toolChoice": {"tool": {"name": "extract_order_info"}},  # このツールの呼び出しを強制
}
```

- Text-to-SQLは「モデルに事実を答えさせない」設計そのものがハルシネーション対策になっている点がポイント。**モデルの役割を「自然言語→構造化クエリの翻訳」に限定**し、事実の取得は決定的な処理（SQL実行）に委ねる
- 同様の考え方は「モデルに計算させず、コード実行（Code Interpreter的な機能）や外部ツール呼び出しに委ねる」パターンにも当てはまる（数値計算の直接生成はハルシネーションしやすい典型例）

### Guardrails以外の補助手段

| 手段 | 概要 | 使いどころ |
|------|------|------------|
| セマンティック類似度検証 | 生成された応答と参照ソースをそれぞれEmbeddingモデル（Titan Embeddings等）でベクトル化し、コサイン類似度を計算。しきい値を下回ったら「ソースから逸脱した回答」として棄却・再生成・人間レビューに回す | Contextual Grounding Checkが使えない構成（Bedrock以外のモデル、Guardrails未導入のパイプライン等）でも自前で実装できる、簡易的なグラウンディング検証。NLIベースのGrounding Checkより粗いが、実装コストが低い |
| 多重生成と一致確認（Self-consistency） | 同じプロンプトに対して複数回（温度パラメータ`temperature`を上げて）生成させ、回答が一致するかを確認する。分類・抽出のように答えが離散的なタスクでは多数決（majority vote）で最終回答を決める、回答が割れた場合は信頼度が低いとみなして人間レビューに回す、といった使い方 | 単一生成だと運悪く外れ値的な出力が採用されてしまうリスクを、複数サンプルの合意形成で緩和したい場合。コストは生成回数分増える点がトレードオフ |

- どちらもBedrock側の機能ではなく、**アプリケーション側で実装する信頼性向上パターン**である点が試験のひっかけになりやすい（「Guardrailsの機能である」という誤答選択肢に注意）
- セマンティック類似度検証とContextual Grounding Checkは目的が似ているが、後者はAWSマネージドでNLIベースの含意判定を行うのに対し、前者は自前で埋め込みベクトルの距離を計算するだけの簡易版、という違いを押さえておく

## 試験でのひっかけポイント整理

- 「Guardrailsを設定すれば有害コンテンツやハルシネーションを完全に防げる」→ 誤り。Guardrailsは多層防御の1層であり、単体で100%の防御を保証しない。プロンプトエンジニアリング・出力検証・人間レビュー等と組み合わせるのが前提
- 「Guardrailsはモデル呼び出し（Converse/InvokeModel）とセットでしか使えない」→ 誤り。`ApplyGuardrail` APIにより、モデル呼び出しと独立に単体でテキストを評価できる
- 「Contextual Grounding Checkは、参照ソースなしの自由生成にも使える汎用ハルシネーション対策機能である」→ 誤り。参照ソース（RAGの検索結果等）とモデル応答の関係を評価する機能であり、ソースが存在する構成が前提
- 「PROMPT_ATTACKフィルターは出力側にも強度設定する意味がある」→ 誤り。プロンプトアタックは入力（ユーザーからの指示）に対する攻撃であり、出力側への適用は意味を持たない
- 「セマンティック類似度検証や多重生成による一致確認は、Bedrock Guardrailsの機能の一部である」→ 誤り。これらはGuardrailsに含まれず、アプリケーション側で実装する補助的な信頼性向上パターン
- 「数値を伴う質問にはモデルに直接答えさせる方が高精度になる」→ 誤り。数値・事実の生成はハルシネーションが起きやすく、Text-to-SQLのようにモデルの役割を「クエリ生成」に限定し、実際の値はデータソースの実行結果から取得する方が信頼性が高い
- 「ClassicティアでもPROMPT_ATTACKフィルターを最高感度にすれば、プロンプトリーケージも含めて全種類のプロンプト攻撃を検出できる」→ 誤り。プロンプトインジェクション・ジェイルブレイクはどちらのティアでも検出できるが、プロンプトリーケージ検出はStandardティア限定の機能でClassicティアでは対応外
- 「InvokeModel APIでGuardrailsのプロンプト攻撃フィルターを有効にするには、Guardrailを作成してguardrailConfigを指定するだけでよい」→ 誤り。InvokeModel系APIはConverse APIと違いメッセージ構造で入力/指示を区別しないため、呼び出し側でユーザー入力をXMLタグ（`<amazon-bedrock-guardrails-guardContent_{suffix}>`）で囲む実装が別途必要。これを省略するとフィルターが機能しない
- 「Guardrailsのタグのsuffixは固定値で問題ない」→ 誤り。固定のタグ名だと悪意あるユーザーがタグを閉じる文字列を入力に混ぜて後続を指示として注入する攻撃が成立するため、リクエストごとにランダムなsuffixを使うことが推奨されている
