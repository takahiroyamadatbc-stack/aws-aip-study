# RAG（Retrieval Augmented Generation）の基本

Bedrock Knowledge Bases / Agentsでの実装詳細（データソース、パーサー、チャンク戦略、API、Agent構成など）は [22-bedrock-knowledge-bases-and-agents.md](22-bedrock-knowledge-bases-and-agents.md) を参照。このノートはRAGそのものの基本原理と、AWS上の選択肢比較・提供元によらない高度な技術を扱う。

## これは何か・なぜ必要か

FM（基盤モデル）は事前学習時点の知識しか持たず、以下の弱点がある。

- **知識のカットオフ**: 学習後に発生した情報や、学習データに含まれない社内固有の情報を知らない
- **ハルシネーション**: 知らないことでも自然な文章で答えてしまう
- **再学習コストの高さ**: 最新情報を反映するたびにFineTuning/事前学習をやり直すのは非現実的

RAGは、FMを再学習せずに、**推論時に外部知識ソースから関連情報を検索し、プロンプトに埋め込んでから生成させる**ことでこれらを解決するアーキテクチャパターン。FM自体の重みは変更しない点がFineTuningとの根本的な違い。

## 基本的な仕組み: Indexing → Retrieval → Generation

RAGは大きく3フェーズに分かれる。**Indexing（事前準備）は1回（または定期更新）**、**Retrieval → Generationは推論のたびに毎回**実行される、という非同期性がポイント。

### 1. Indexing（事前準備フェーズ）

```
生データ(PDF/HTML/DB等) → ロード → チャンク分割 → Embedding化 → ベクトルDBへ格納
```

- **ロード**: S3・Webクローラ・Confluence・SharePointなど様々なソースから元データを取得
- **チャンク分割（Chunking）**: 元データをFMのコンテキスト長やEmbeddingモデルの入力上限に収まる単位に分割する。分割サイズ・重なり幅（overlap）の設計が検索精度を大きく左右する
- **Embedding化**: チャンクをEmbeddingモデル（例: Amazon Titan Text Embeddings、Cohere Embed）に通し、意味を表す高次元ベクトルに変換する
- **ベクトルDBへ格納**: ベクトルと元テキスト・メタデータをベクトルストア（OpenSearch、pgvector、Pineconeなど）にインデックスする

### 2. Retrieval（検索フェーズ）

```
ユーザーの質問 → Embedding化 → ベクトル類似度検索 → 関連チャンクTop-K取得
```

- ユーザーの質問文を、Indexingと**同じEmbeddingモデル**でベクトル化する（モデルが違うとベクトル空間が一致せず検索が成立しない）
- ベクトルDBに対してコサイン類似度などで近傍探索（k近傍探索）を行い、関連度の高いチャンクを上位K件取得する
- 単純なセマンティック検索だけでなく、以下のような手法を組み合わせることで検索精度を高められる

| 手法 | 何をするか | 得意なこと／解決すること |
|------|------------|----------------------------|
| セマンティック検索（Semantic search） | クエリと文書をEmbeddingベクトル化し、ベクトル空間上の類似度（コサイン類似度等）で近傍探索する | キーワードが完全一致しなくても、意味が近ければヒットさせられる（言い換え・同義語に強い） |
| ハイブリッド検索（Hybrid search） | セマンティック検索（ベクトル類似度）とキーワード検索（BM25等の全文検索）を組み合わせ、両方のスコアを統合してランキングする | セマンティック検索が苦手な固有名詞・型番・専門用語などの完全一致重視のクエリを補う |
| メタデータフィルタリング（Metadata filtering） | チャンクに付与したメタデータ（部署・日付・カテゴリ等）の条件で検索対象を絞り込む | 意味的関連性ではなく、権限・鮮度・カテゴリなど構造的な条件で検索範囲を制限したい |
| リランキング（Reranking） | 一次検索で広めに取得した候補（Top-N）を、より高精度な専用リランクモデルで再スコアリングし直す | 一次検索（ベクトル類似度）だけでは細かい関連性の順位付け精度が不足する場合に、最終的な上位K件の精度を上げる |

これらは排他的な選択肢ではなく、**組み合わせて使うのが基本**。典型的な適用順序は「①メタデータフィルタリングで候補集合を絞り込む → ②セマンティック検索／ハイブリッド検索でTop-N候補を取得する → ③リランキングで最終的な順位を並べ替え、上位K件を生成フェーズに渡す」という流れになる。各手法をBedrock Knowledge Basesでどう指定するかは[22-bedrock-knowledge-bases-and-agents.md](22-bedrock-knowledge-bases-and-agents.md)を参照。

### 3. Generation（生成フェーズ）

```
(取得したチャンク + 元の質問) をプロンプトに合成 → FMに投入 → 回答生成
```

- 取得したチャンクを「コンテキスト」としてプロンプトに埋め込み、「このコンテキストの範囲内で回答せよ」という指示とともにFMに渡す（プロンプト拡張）
- FMは学習済みの知識ではなく、**渡されたコンテキストに基づいて**回答を生成するため、最新情報・社内固有情報への対応とハルシネーション抑制の両方が期待できる
- 出典（どのチャンク／ドキュメントを根拠にしたか）を合わせて返すCitation機能を持つ実装も多い

## AWSにおけるRAGの選択肢比較

| 観点 | Amazon Q Business | Bedrock Knowledge Bases | 自己ホストRAG |
|------|-------------------|--------------------------|----------------|
| 位置づけ | フルマネージドの**エンドユーザー向けチャットアプリ** | 開発者がアプリに組み込む**RAGビルディングブロックAPI** | 自前で全パイプラインを構築 |
| 想定利用者 | 業務ユーザー（コード不要で使える） | アプリ開発者（API/SDK経由で呼ぶ） | インフラ・MLエンジニア |
| データ接続 | 50+のビルトインコネクタ（S3, SharePoint, Salesforce, Slack, Confluence等）を設定するだけ | データソースコネクタ（S3, Web Crawler, Confluence, Salesforce, SharePoint等）をKB側で設定 | 自前でETL/ローダーを実装 |
| Embedding/チャンク戦略 | 内部で自動処理（ユーザーは選べない） | Titan/Cohere等から選択可、チャンク戦略も複数選択可、Lambdaでカスタムチャンクも可 | 完全に自由（独自Embeddingモデルも可） |
| ベクトルストア | 非公開（内部管理） | OpenSearch Serverless / Aurora PostgreSQL(pgvector) / Pinecone / Redis Enterprise Cloud / MongoDB Atlas から選択 | 自由に選定・運用 |
| カスタマイズ性 | 低い（UI・権限設定が中心） | 中〜高（チャンク・検索方式・プロンプトテンプレートを制御可） | 最も高い（全レイヤーを制御） |
| 運用負荷 | ほぼゼロ（フルマネージド） | 低い（ベクトルDBの一部はサーバーレス選択可） | 高い（自前でスケーリング・監視） |
| アクセス制御 | ID連携（IAM Identity Center）でユーザー単位のACLをそのまま検索結果に反映（ドキュメントレベルのアクセス許可を尊重） | データソース単位、メタデータフィルタでの制御が中心 | 自前で実装が必要 |
| 主な用途 | 社内ナレッジ検索チャットボットをすぐ使いたい | 独自GenAIアプリ（Bedrock Agentsとも統合）にRAGを組み込みたい | 既存の社内ベクトル基盤がある／特殊なEmbeddingモデルを使いたい／ベンダーロックインを避けたい |

**選び方の基本方針**: 「すぐに使える社内検索チャット」ならAmazon Q Business、「自社アプリにRAG機能を組み込みたい・生成部分もアプリ側で制御したい」ならBedrock Knowledge Bases、「既存ベクトル基盤がある／特殊要件がある」なら自己ホスト、という順で検討する。

## 高度なRAG技術

基本形（素朴なRAG／Naive RAG）は「クエリをそのままEmbedding化して検索する」だけだが、クエリの質・関係性の複雑さによって精度が頭打ちになる。これを補うための拡張手法群。

### クエリ前処理（Pre-Retrieval）

検索（Retrieval）の**前段**で、ユーザーの生クエリをそのまま使わず加工してから検索にかける手法群。「検索する前にクエリ自体を良くする」というアプローチ。

| 手法 | 概要 | 何を解決するか | 実装方法（簡易） |
|------|------|-------------------|--------------------|
| クエリ拡張（Query Expansion） | 元クエリに同義語・関連語・言い換え候補を追加し、複数のバリエーションで検索する | 短い/曖昧なクエリでは表現の揺れにより関連チャンクを取りこぼす（再現率が低い）問題を解決する | LLMに元クエリの言い換えを複数生成させ（multi-query）、それぞれで検索して結果をマージする。または同義語辞書を使う |
| クエリ分解（Query Decomposition） | 複数の観点を含む複合質問を、複数のサブクエリに分解し、それぞれ個別に検索してから統合する | 「AとBを比較して」「Xの条件下でYはどうなる」のような複合質問は、単一のベクトル検索では網羅できない問題を解決する | LLMに「この質問に答えるために必要なサブ質問は？」と分解させるプロンプトを実行し、サブクエリごとに検索→結果を統合してから生成に渡す |
| クエリ変換（Query Transformation / Rewriting） | ユーザーの曖昧・口語的・会話依存のクエリを、検索に適した形に書き換える | 会話履歴中の指示語（「それ」「さっきの」等）の解決（coreference resolution）や、ユーザーの語彙とドキュメントの語彙の乖離を解決する | LLMによる書き換えプロンプトを検索前に挟む。抽象化した質問に変換してから検索する「ステップバックプロンプティング」もこの一種 |
| HyDE（Hypothetical Document Embeddings） | クエリを直接Embedding化するのではなく、まずLLMに「クエリへの仮想的な回答文書」を生成させ、その**仮想文書の方**をEmbedding化して検索に使う | 質問文と回答文はEmbedding空間上でスタイル・語彙が異なりやすく、クエリをそのままEmbedding化すると類似度が下がる（クエリ-ドキュメント間の言語的ギャップ）問題を解決する | LLM呼び出し（仮想文書生成）→ その仮想文書をEmbedding化 → ベクトル検索、という2段構成をアプリ側で実装する |

これらは**Retrieve/RetrieveAndGenerate呼び出し前のアプリケーション側の処理**として実装するのが基本形（Bedrock Knowledge Bases自体に「クエリ拡張オン/オフ」のような単純なスイッチがあるわけではなく、LLM呼び出しを挟むオーケストレーションとして組む）。Bedrock Agentsを使う場合は、Agentのオーケストレーション（プロンプトチェーンの中でクエリ分解・書き換えを行わせる）に組み込む形で実現することが多い。

### GraphRAG

| 項目 | 内容 |
|------|------|
| 解決したい課題 | 通常のベクトルRAGはチャンク単位の意味的類似度で検索するため、**複数のエンティティ・複数ホップにまたがる関係性を辿る質問**（例:「Aが所属する部署のマネージャーが承認した契約は？」）に弱い |
| アプローチ | ドキュメントからエンティティ（人・組織・製品等）とその関係性を抽出し、ナレッジグラフとして構築。検索時はベクトル類似検索に加えて、グラフの探索（トラバーサル）で関連エンティティ・関係も辿ってコンテキストに含める |
| 検索時の挙動 | ベクトル類似検索でエントリーポイントとなるノード（関連度の高いエンティティ）を特定し、そこからグラフを探索して関連するエンティティ・関係もあわせてコンテキストに追加する |
| 向いているケース | 組織図、サプライチェーン、権利関係、規約間の参照関係など、**エンティティ間の明示的な関係性**が重要なドメイン。「誰が」「何を」「どう関係しているか」を跨いで答える必要がある質問 |
| 通常のベクトルRAGとの違い | チャンク単位の意味的類似度だけでなく、ドキュメントをまたいだ**明示的な関係（誰が誰の上司か等）**を構造的に辿れる点 |

**使い分けの目安**: 単純な「関連文書を探して要約する」タイプの質問には通常のベクトルRAGで十分。「複数のエンティティ間の関係を辿らないと答えが出せない」マルチホップ質問が多いドメインでは、GraphRAGの採用を検討する。AWSでの実装（Amazon Neptune Analytics + Bedrock Knowledge Bases）は[22-bedrock-knowledge-bases-and-agents.md](22-bedrock-knowledge-bases-and-agents.md)を参照。

## 試験でのひっかけポイント整理

- 「チャンク戦略はどれを選んでも精度に差は出ない」→ 誤り。ドキュメントの構造（表が多い、長文か短文か等）によって適したチャンク戦略は異なる
- 「Embeddingモデルはクエリ側とインデックス側で別々のものを使ってよい」→ 誤り。同一のEmbeddingモデルでベクトル空間を揃える必要がある
- 「RAGを使えばFineTuningは不要になる」→ 一概に誤り。RAGは知識注入（What）に強く、口調・出力フォーマットの一貫性（How）はFineTuningの方が向く場合がある。両者は目的が異なり併用もされる
- 「Amazon Q BusinessもBedrock Knowledge Basesも同じレベルのカスタマイズ性を持つ」→ 誤り。Amazon Qはエンドユーザー向けフルマネージドアプリでカスタマイズ性は低く、Bedrock KBは開発者がアプリに組み込むビルディングブロックでカスタマイズ性が高い
