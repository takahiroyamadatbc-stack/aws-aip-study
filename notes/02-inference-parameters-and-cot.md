# 推論パラメータ（温度）とChain-of-Thoughtプロンプティング

FMの出力を「事実に忠実にするか／多様にするか」「精度をどう上げるか」を調整する基本手段。温度パラメータの向きと、CoTの仕組み・レイテンシへの影響は混同しやすいので、まず仕組みから押さえる。

## 温度パラメータ（temperature）とは

FMはテキストを生成するとき、直前までの文脈を踏まえて「次に来るトークン候補それぞれの確率」を計算し（softmaxで確率分布に変換）、そこから1つを選んでいる。温度はこの**確率分布の形をスケーリングするパラメータ**で、選び方そのもの（サンプリング）を変える。

- **温度を上げる**（1.0に近い、あるいはそれ以上）→ 確率分布が平坦化される → 本来なら選ばれにくい低確率トークンにも選ばれるチャンスが増える → 出力の**多様性・ランダム性が増す**
- **温度を下げる**（0に近い）→ 確率分布が尖る → 最も確率の高いトークンに集中して選ばれる → 出力が**決定論的・保守的**になる（0にすると常に最尤トークンを選ぶ＝実質グリーディ選択）

覚え方: 温度は物理の温度と同じ比喩で理解すると向きを取り違えにくい。温度を上げる＝分子（確率質量）が拡散して自由に動き回る＝多様性が増す。温度を下げる＝凝縮して一箇所に集中する＝決定論的になる。「温度＝創造性のダイヤル」とセットで覚える。

### ハルシネーションとの関係

低確率トークンが選ばれやすくなるということは、ソース文書や事実に基づかない「もっともらしいがそれらしいだけの語」を拾うリスクが上がるということ。したがって**ハルシネーション削減には温度を下げるのが基本方針**。「温度を上げる」を含む選択肢がハルシネーション対策として出てきたら、原則として誤答と判断してよい。

### 例外: 温度を上げるのが正しい場面もある

[[30-bedrock-guardrails-and-reliability]]で扱った**Self-consistency（多重生成と一致確認）**は、あえて温度を上げて同じプロンプトから複数回生成させ、回答の一致度・多数決で最終回答の信頼度を判断する手法。これは「1回の生成の中でランダム性を許容する代わりに、複数サンプルの合意で精度を担保する」設計であり、「温度を上げる＝常にハルシネーションが増える」という単純な理解だけでは説明がつかない例外パターンとして区別しておく。ただし単発の要約・QAタスクで温度だけを上げてハルシネーション対策と称する選択肢は誤り、という基本方針は変わらない。

## Chain-of-Thought（CoT）とは

CoTは、モデルに最終的な答えをいきなり出させるのではなく、**途中の推論ステップを言語化させてから結論を出させる**プロンプティング手法。人間が暗算よりも途中式を書いた方が計算ミスが減るのと同じ発想で、モデルにも「考える過程」をトークンとして生成させることで、事実確認・論理展開の精度を上げる。

| 種類 | プロンプトの中身 | 特徴 |
|---|---|---|
| **Few-shot CoT** | 「入力＋ステップバイステップの模範解答」の例を複数個、プロンプトに埋め込む | 入力プロンプトが長くなる（例示の分）。処理時間・コストが増えやすい |
| **Zero-shot CoT** | 例示なしで「ステップバイステップで考えてください」の一文を追加するだけ | 入力プロンプトはほぼ変わらない。追加のAPI呼び出し・外部検索・別サービス連携は一切発生しない |

要約タスクにCoTを組み込むと、モデルは「ソース文書のどの記述に基づいて、どう要約するか」を段階的に確認しながら生成することになり、ソースに存在しない情報を生成しにくくなる（＝ハルシネーション抑制）。

### レイテンシへの影響（誤解しやすいポイント）

CoTを見て「推論ステップが増える＝時間がかかる」と直感的に思いがちだが、これは**Zero-shot CoTと処理全体のアーキテクチャを混同した誤解**であることが多い。整理すると以下の通り。

- Zero-shot CoTで増えるのは**出力トークン数**（思考過程＋最終要約の分）だけ。入力プロンプトはほぼ変わらず、モデル呼び出しは**単一パス（1回のAPI呼び出し）で完結**する
- 対して、RAG（検索→生成の2段階）や、Guardrailsの後処理チェック（生成後に別途評価）は、**呼び出しやネットワーク往復自体が増える**構成
- 「追加のインフラ・別サービス呼び出しが要らない」という点で、CoTはRAGよりレイテンシー・スループット要件に対して軽い施策になり得る。出力トークンが多少増える分の生成時間増はあるが、それは「もう1回APIを呼ぶ」「別サービスに問い合わせる」ほどのオーバーヘッドではない

## Extended Thinking（拡張思考）とは

Extended thinkingは、Anthropic Claudeモデル（Bedrock経由でも利用可）自体が持つ**モデル機能**で、CoTのような「プロンプトでステップバイステップに考えるよう指示するテクニック」とは別物。APIパラメータとして**thinkingバジェット（トークン数）**を指定すると、モデルは最終回答を出す前に、そのバジェット内で内部的な思考過程（thinkingブロック）を生成してから回答する。

- **最小バジェットは1,024トークン**。Anthropicは最小値から始めて必要に応じて段階的に増やすことを推奨している
- CoTが「プロンプトの書き方」で誘導する手法なのに対し、extended thinkingは**モデル呼び出し自体のパラメータ**として思考プロセスの生成を制御する点が違う
- thinkingブロックの分だけ**出力トークンが増える**ため、単純なZero-shot CoTより生成トークン数の増加幅が大きくなりやすく、レスポンスレイテンシーが伸びる方向に働く
- あくまで「モデルの推論能力を高める」機能であり、**企業データソースからの検索・取得機能は持たない**。ソースドキュメントへの引用・帰属（citations）が要件にある問題では、extended thinkingだけでは満たせず、RAG（[[21-rag-basics]]、Bedrock Knowledge BasesのRetrieveAndGenerate API）が別途必要になる

### 他プロバイダーにおける同種機能（参考知識）

「Extended thinking」という名称・APIパラメータ（`thinking`、`budget_tokens`）自体はAnthropic/Claude固有の実装だが、**モデルが最終回答の前に内部で思考トークンを生成する**という同種の機能は他社モデルにも存在する（名称・API仕様は異なる）。

| プロバイダー/モデル | 該当機能 | 特徴 |
|---|---|---|
| Anthropic Claude | Extended thinking | `budget_tokens`でトークン予算を明示指定、thinkingブロックが応答に含まれる |
| OpenAI（o1/o3/GPT-5系reasoningモデル） | Reasoning effort | `reasoning_effort`パラメータで制御。内部の思考過程自体は非公開で要約のみ返る |
| Google Gemini（2.5系） | Thinking budget | Claudeと同様「thinking budget」という用語を使う |
| DeepSeek R1 | 推論トークン | 思考過程がほぼそのまま可視化される |

AIP-C01はBedrock試験であり、AWS外のモデル仕様そのものが直接問われる可能性は低いが、Bedrockが複数プロバイダーのモデルをホストする以上、「Extended thinkingパラメータが使えるか」は呼び出し先がAnthropic Claudeかどうかに依存する、という前提は押さえておく。

### 誤答しやすいポイント

「ステップバイステップの推論を示す」という要件文だけを見て、CoTと同様の軽い施策だと思い込みextended thinkingを選ぶと、以下の2点で外れる可能性がある。

1. **引用・ソース帰属の要件を満たさない**（検索機能がないため）
2. **レイテンシー要件に反する**（thinkingトークン生成で応答が遅くなる。上記「CoTのレイテンシへの影響」と混同しないこと。CoTは軽量、extended thinkingは相応の負荷増）

## 試験の勘所（AIP-C01 実例）

ハルシネーション削減＋高スループット（1,000件/時）＋低レイテンシ（3秒/件）を同時に満たす問題では、次の判断基準が効く。

1. **温度を上げる選択肢** → 基本的に誤り（Self-consistency文脈でない限り）
2. **RAG（ナレッジベース＋セマンティックチャンキング）** → ソースに基づかせる（グラウンディング）ための王道。長文書でもチャンク分割で関連部分だけ検索するためコンテキストウィンドウの制約も回避できる
3. **Zero-shot CoT** → 追加インフラ不要でハルシネーションを抑えつつ、単一パス呼び出しのままレイテンシー要件を維持できる。「追加のAPI呼び出しやインフラが不要」という説明文が出たらCoTを積極的に疑ってよい
4. **Guardrailsによる出力ブロック（パターンマッチ）** → Contextual Grounding Checkや自動推論チェックは実在する機能だが、参照ソースなしの「パターンマッチ」でのハルシネーション検出はできない。生成後のブロックである以上、生成品質そのものの改善（RAG・CoT）の代替にはならない点にも注意
