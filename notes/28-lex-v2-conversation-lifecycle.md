# Amazon Lex V2の会話ライフサイクルとFM連携

## Amazon Lex V2とは何か

**Amazon Lex V2**は、音声・テキストによる会話型インターフェース（チャットボット、音声アシスタント、IVR＝自動音声応答システム等）を構築するためのフルマネージドサービス。Amazon Alexaと同じ音声認識・自然言語理解の技術基盤がベースになっている。

生成AI（Bedrock）が「自由な入力から自由な文章を生成する」ことを得意とするのに対し、Lex V2は**「ユーザーが何をしたいか（インテント）」を決まった選択肢の中から正確に分類し、その実行に必要な情報（スロット）を漏れなく聞き出す**ことに特化したサービス。「今日は何が食べたい気分ですか」に自由な感想文で答えさせるのではなく、「ピザの注文を受け付け、サイズと配達先住所を確実に聞き出す」といった、**目的が明確で入力の型を厳密に管理したい会話**を作るのに向いている。

- ASR（Automatic Speech Recognition／自動音声認識）とNLU（Natural Language Understanding／自然言語理解）を組み合わせたサービスで、音声入力・テキスト入力の両方に対応する
- V1からの主な強化点: 1つのボットで複数言語を同時サポート、1つの発話から複数インテントを扱う機能、会話フローの分岐（Conditional Branching）など。試験ではV1/V2の細かい差分より、**V2の会話ライフサイクル（後述）とLambda連携の仕組み**が問われやすい
- Amazon Connect（コンタクトセンターサービス）と統合してIVRの音声対話を構築する用途や、Webサイト・アプリに埋め込むテキストチャットボットの用途で使われる

## 会話ライフサイクル: インテント認識 → スロット収集 → フルフィルメント

Lex V2の会話は次の3段階で進む。

```
ユーザー発話
  → ① インテント認識（NLU）: 「これは何をしたいという意図か」を分類
  → ② スロット収集: インテントの実行に必要なパラメータを1つずつ聞き出す
  → ③ フルフィルメント: 必要な情報が揃った後、実際にその意図を「実行」する
```

| 段階 | 内容 |
|------|------|
| インテント（Intent） | 「注文を確認したい」「予約を変更したい」のようなユーザーの目的そのもの。ボット作成時に発話例（Sample Utterances）を複数登録し、NLUがそれを学習して自由な言い回しをインテントに分類できるようにする |
| スロット（Slot） | インテントを実行するのに必要な変数。「注文番号」「日付」など。スロットタイプ（`AMAZON.Number`、`AMAZON.Date`、独自定義のカスタムスロットタイプ等）ごとに値の妥当性検証・聞き方（プロンプト文言）を定義する。全スロットが埋まるまでLexは対話的に聞き返す |
| フルフィルメント（Fulfillment） | スロットが揃った後、「実際にその処理をやる」段階。ここで初めて在庫確認・注文実行・DB更新などの外部処理を呼び出す |

重要なのは、Lexが受け持つのは①②の**入力理解**（相手が何を言っていて、何の情報を渡してきたかを構造化する部分）で、③フルフィルメントは**その構造化された情報を使って何かを実行する**部分だという点。この境目が、Lex V2に生成AIを組み合わせる設問の分岐点になりやすい。

## Lambdaフック — Lex V2が外部処理を挟む唯一の穴

Lex V2はボット定義（インテント・スロットの設定）だけでは完結しない処理（在庫確認、動的な応答生成など）を、**Lambda関数のフック**という形でしか挟めない。1つのボットエイリアス（言語単位）に1つのLambda関数を紐づけ、以下のタイミングで呼び出せる。

| フックポイント | 主な用途 |
|---|---|
| インテント認識直後の初期化（Initialization） | セッション属性の事前設定など |
| 各スロット取得後（Validation） | スロット値のカスタムバリデーション |
| 確認プロンプト時 | 確認前の追加チェック |
| **フルフィルメント時** | 実際の処理実行、外部API呼び出し |
| クローズ前 | 最終応答文のカスタマイズ |

LambdaはLexから渡されるJSON（インテント名・スロット値・セッション状態）を受け取り、Lexが定めるレスポンス形式のJSONを返すという契約になっている。**Lambda内部の実装は完全に自由**なので、Bedrockの`InvokeModel`をLambda内から呼ぶことも、他の任意のAPI呼び出しと同じように成立する。Lex V2自体にBedrockエンドポイントを直接指定するようなノーコード統合は存在しない。

## フルフィルメントでのBedrock連携パターン

既存のインテント認識・スロット抽出をそのまま維持しつつ、FMによる自然な応答生成を追加したい場合は、フルフィルメントLambda内でBedrock Runtimeの`InvokeModel`（または`Converse`）APIを呼び出す構成にする。

```python
import json
import boto3

bedrock = boto3.client("bedrock-runtime")

def lambda_handler(event, context):
    intent_name = event["sessionState"]["intent"]["name"]
    slots = event["sessionState"]["intent"]["slots"]
    user_input = event["inputTranscript"]

    # Lexが確定させたインテント・スロット値を使ってプロンプトを構築する
    prompt = f"""ユーザーの問い合わせ: {user_input}
インテント: {intent_name}
抽出済みスロット: {json.dumps(slots, ensure_ascii=False)}

上記の内容を踏まえ、丁寧で具体的な回答文を作成してください。"""

    response = bedrock.converse(
        modelId="anthropic.claude-3-5-sonnet-20241022-v2:0",
        messages=[{"role": "user", "content": [{"text": prompt}]}],
    )
    answer_text = response["output"]["message"]["content"][0]["text"]

    return {
        "sessionState": {
            "dialogAction": {"type": "Close"},
            "intent": {"name": intent_name, "state": "Fulfilled"},
        },
        "messages": [{"contentType": "PlainText", "content": answer_text}],
    }
```

- Lambda実行ロールに`bedrock:InvokeModel`（または`bedrock:Converse`）を許可するIAMポリシーが前提条件
- 既存のNLUレイヤー（インテント・スロット定義）は一切変更不要で、Lambda実装の追加だけでFM推論を組み込める点が、この構成の最大のメリット

## Assisted NLUとの違い（「理解精度向上」と「応答生成」は別レイヤー）

**Assisted NLU**は、LLMを使ってインテント分類・スロット解決の**理解精度**を向上させるLex V2の機能。設定済みのインテント・スロットの範囲内で動作し、トレーニングデータ（発話例）が少なくてもインテントを正確に認識しやすくなる、という②の精度改善に特化した機能。

- ボットが返す応答テキストの生成・変更は行わない。「理解精度（入力解釈＝②）を高める機能」と「応答生成（出力生成＝③フルフィルメント以降）」は別の処理レイヤーにあり、混同しやすい
- ユーザーへ返す自由形式の回答文を生成したい場合は、Assisted NLUを有効にするだけでは足りず、別途Lambda＋Bedrockのような構成が必要になる

## Bedrock Agentsとの違い（役割が別物、単純な置き換えではない）

**Bedrock Agents**は、FMを中心にAction Group（外部API・Lambda）とKnowledge Base（RAG）をオーケストレーションし、複数ステップのタスクをFM自身が自律的に計画・実行する（ReActパターン）サービス。詳細は[22-bedrock-knowledge-bases-and-agents.md](22-bedrock-knowledge-bases-and-agents.md)を参照。

| 観点 | Amazon Lex V2 | Amazon Bedrock Agents |
|------|----------------|--------------------------|
| 意図理解の方式 | 事前定義したインテント・スロットに対する決定的（deterministic）な分類 | FM自身が次に何をすべきかをその都度推論（ReAct） |
| 得意なこと | 目的が明確で、入力の型を厳密に管理したい会話（注文・予約など） | 未知のタスクをFMが動的に計画・実行する自由度の高い会話 |
| 既存資産の扱い | インテント・スロット・Lambda連携をそのまま使い続けられる | Lex V2からの移行にはインテント定義・スロット設計をAction Groupとして再設計し直す必要がある |

Lex V2ボットをBedrock Agentsに置き換えることは、既存のインテント定義・スロット設計・Lambda連携をすべてAction Groupとして再設計することを意味し、「既存ロジックを変更せず最小コストで機能追加する」という要件とは方向性が逆になる。

- なお、Lex V2には`BedrockAgentIntent`という機能があり、Lex V2ボットの中の特定インテントの処理をBedrock Agentsに委譲する連携は可能。ただしこれは「Lex V2ボットを廃止してAgentsに全面移行する」こととは別物で、Lex V2の会話フロー自体は維持されたまま一部インテントの処理だけをAgentsに渡す構成になる

## 試験でのひっかけポイント整理

- 「Lex V2のフルフィルメントは、Bedrock Knowledge Basesのエンドポイントをコード不要で直接指定できる」→ 誤り。フルフィルメントはLambda関数を呼び出す設計になっており、KBを使うにも依然としてLambda経由の実装が必要
- 「FMによる自然な応答生成を追加するには、既存のLex V2ボットをBedrock Agentsに全面移行する必要がある」→ 誤り。既存のインテント・スロット・Lambda連携を維持したまま、フルフィルメントLambda内でBedrockのInvokeModel/Converse APIを呼ぶだけで実現できる。Agentsへの全面移行は既存資産の再設計コストが大きく、要件（コスト・工数最小化）に反する
- 「Assisted NLUを有効化すれば、FMによる自然な応答文が自動生成される」→ 誤り。Assisted NLUはインテント分類・スロット解決の理解精度（②）を高める機能であり、応答テキストの生成（③以降）は対象外
- 「インテント・スロットとフルフィルメントは同じ処理レイヤーである」→ 誤り。インテント・スロットは「ユーザーの入力を構造化して理解する」段階、フルフィルメントは「構造化された情報を使って何かを実行する」段階で、役割が異なる
- 「Lex V2ボットにはLambda関数を複数紐づけられる」→ 誤り。1つのボットエイリアス（言語単位）に紐づけられるLambda関数は1つ。複数のフックポイント（初期化・バリデーション・フルフィルメント等）はすべて同じLambda関数内で分岐処理する
