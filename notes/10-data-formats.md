# データフォーマット（CSV, JSON, Avro, Parquet, ORC）

学習データ・RAGの元データ・データレイク上の保管形式として、どのフォーマットを選ぶかは「基盤モデルの統合、データ管理」領域で問われる。特にAvro/Parquet/ORCは業務でJSON/CSVほど馴染みがなく、AWSサービス（Athena, Glue, Kinesis, EMR, Redshift等）との組み合わせで名前だけ出てくることが多いので、まず**それぞれが何であるか（内部構造・設計思想）**から整理する。

## 最初に押さえる軸: テキスト形式か バイナリ形式か、行指向か 列指向か

4つのフォーマットを分類する軸は主に2つある。

- **テキスト形式 / バイナリ形式**: 人間がエディタで開いてそのまま読めるか（テキスト）、専用のライブラリを介さないと解釈できないか（バイナリ）
- **行指向（Row-oriented） / 列指向（Column-oriented）**: ディスク上でデータをどう並べるか

行指向・列指向の違いがAvroとParquetの使い分けを理解する鍵になる。

```
行指向（Row-based）のイメージ:
  [id1,name1,age1] [id2,name2,age2] [id3,name3,age3] ...
  → 1レコード分のデータが物理的に隣接して格納される

列指向（Columnar）のイメージ:
  [id1,id2,id3,...] [name1,name2,name3,...] [age1,age2,age3,...]
  → 同じ列の値同士が物理的に隣接して格納される
```

- 行指向は「1レコードを丸ごと読み書きする」処理（1件ずつのINSERT、全項目を使うトランザクション処理）に強い
- 列指向は「特定の列だけを集計する」処理（`SELECT AVG(age) FROM ...`のような分析クエリ）に強い。使わない列を丸ごと読み飛ばせるためI/Oが減り、さらに同じ型・似た値が並ぶため圧縮効率も高い

| フォーマット | 形式 | 行指向/列指向 | スキーマ | 圧縮効率 | 分析クエリ適性 |
|---|---|---|---|---|---|
| **CSV** | テキスト | 行指向（フラットな表のみ） | なし（型情報を持たない） | 低い | 低い（毎回全列を読む） |
| **JSON** | テキスト | 行指向（レコード単位、階層構造可） | なし（緩いスキーマ、キー名を毎レコード保持） | 低い | 低い |
| **Avro** | バイナリ | 行指向 | あり（ファイルに埋め込み or スキーマレジストリ） | 中程度 | 中〜低（分析には不向き） |
| **Parquet** | バイナリ | 列指向 | あり（ファイルフッターに埋め込み） | 高い | 高い |
| **ORC** | バイナリ | 列指向 | あり（ファイルフッターに埋め込み） | 非常に高い | 高い（特にHive/EMR経由） |

## CSV（Comma-Separated Values）

- 最もシンプルなテキスト形式。1行1レコード、カンマ区切りでフラットな表形式データのみ表現できる
- 型情報を一切持たない（すべて文字列として保存され、読み込み側が数値/日付などに解釈する）ため、型の取り違えや欠損値表現（空文字か`NULL`か等）が実装依存になりやすい
- 階層構造（配列やネストしたオブジェクト）を表現できない
- **用途**: 表計算ソフトとの受け渡し、SageMakerの学習データ（表形式の教師データ）、簡易なログ・エクスポートなど、人間が中身を目視確認したい小〜中規模データ

## JSON（JavaScript Object Notation）

- テキスト形式で、キー・バリューのペアと配列によるネスト構造を表現できる（CSVにはない柔軟性）
- スキーマを強制する仕組みがない（同じ「レコードの集合」でもレコードごとにキーが違っていても構文上はエラーにならない）ため、大量データでは同じキー名を毎レコード繰り返し書く分だけファイルサイズが膨らみやすい
- **用途**: API・Bedrock/SDKの入出力形式、Bedrock Knowledge Basesに投入する半構造化ドキュメント、設定ファイル、ネスト構造を保ったまま保存したいログ（CloudTrail等）

## Avro（詳しめ）

### これは何か・なぜ生まれたか

Apache Avroは、Hadoopエコシステム（Apache参加プロジェクトの1つ）で生まれた**バイナリの行指向シリアライゼーション（直列化）フォーマット**。もともとの動機は「データを一時的にストレージへ書き出す／ネットワーク越しに送る際に、コンパクトかつ高速に、しかもスキーマの変更に強い形でシリアライズしたい」というもの。今はKafka（Amazon MSK）やKinesisのようなストリーミング基盤でのメッセージフォーマットとして特に多用される。

### 内部構造: データとスキーマが一体（自己記述的）

Avroの最大の特徴は**スキーマ（JSON形式で定義）をデータ本体と一緒に管理する**設計にある。

```json
// Avroスキーマの例（JSON形式で定義する）
{
  "type": "record",
  "name": "User",
  "fields": [
    { "name": "id",    "type": "int" },
    { "name": "name",  "type": "string" },
    { "name": "email", "type": ["null", "string"], "default": null }
  ]
}
```

- `.avro`ファイルはファイル自体のヘッダー部分にこのスキーマを埋め込む（自己記述的）。そのためファイル単体で「どういう構造のデータか」が読み手にわかり、他のシステムと別途スキーマ定義をやり取りする必要がない
- 一方、Kafka/MSKのようなストリーミング用途では**1メッセージごとにスキーマを埋め込むとオーバーヘッドが大きい**ため、スキーマ本体は別サービス（AWS Glue Schema Registry等）に登録し、各メッセージにはスキーマIDだけを持たせる運用が定石。受信側はIDを使ってレジストリからスキーマを引く
- データ本体はスキーマの定義順にバイナリでシリアライズされる（フィールド名を毎回書かないため、JSONより格段にコンパクト）

### スキーマ進化（Schema Evolution）に強い

Avroが「行指向のバイナリ形式」の中でも特に選ばれる理由は、**スキーマが将来変わることを前提に設計されている**点にある。

- 新しいフィールドを追加する際に`default`値を指定しておけば、**古いスキーマで書かれたデータを新しいスキーマで読んでも**（あるいはその逆でも）互換性を保てる（後方互換・前方互換）
- 例えば上記スキーマに新フィールド`phone`（`default: null`）を追加しても、既存の`.avro`ファイルは読み込み時に`phone`が自動的に`null`として補完される
- ストリーミングパイプライン（Kinesis → Lambda → 下流システム、Kafka Producer/Consumerなど）では、送信側と受信側のアプリケーションを同時にデプロイし直せないことが多く、**「送信側だけ先にフィールドを追加した」状態が一定期間発生する**。Avroはこの状況でも壊れずにデータをやり取りできるよう設計されている

### 用途まとめ

- Kafka/Amazon MSK、Kinesisのメッセージフォーマット（AWS Glue Schema Registryと組み合わせる）
- Hadoop/EMR上でのレコード単位の処理（行全体を読み書きするETLのステージング領域）
- スキーマが将来変わることが確実な、システム間データ連携のシリアライズ形式

## Parquet（詳しめ）

### これは何か・なぜ生まれたか

Apache Parquetは、Google Dremelの論文（列指向でのクエリ処理に関する研究）に着想を得て、Twitter社とCloudera社が共同開発した**バイナリの列指向ストレージフォーマット**。目的はAvroとは対照的で、「1レコードを丸ごと扱う」のではなく「巨大なデータセットのうち一部の列だけを高速に集計・分析したい」というOLAP（分析）用途に最適化されている。

### 内部構造: Row Group → Column Chunk → Page

Parquetファイルは単純な列の羅列ではなく、階層的な構造を持つ。

```
Parquetファイル
└─ Row Group（行の集合。数万〜数百万行単位の塊）
    ├─ Column Chunk（列A のデータだけを集めたブロック）
    │   └─ Page（実際に圧縮・エンコードされた最小単位）
    ├─ Column Chunk（列B のデータだけを集めたブロック）
    └─ Column Chunk（列C のデータだけを集めたブロック）
└─ Footer（各Row Group/Column Chunkの位置、統計情報、スキーマを記録するメタデータ）
```

- 1つのファイルの中でも、まず行方向にRow Group単位で分割し、**その中で列ごとにまとめて格納する**（完全な列指向DBではなく、大規模分散処理に向くハイブリッド構造）
- ファイル末尾のFooterに「各列の最小値・最大値」などの統計情報を持つため、クエリエンジンは実データを読む前に「この Row Group には条件に合致する行が存在しない」と判断してブロックごと読み飛ばせる（プレディケートプッシュダウン）
- 同じ列は同じ型・似た値が並ぶため、列単位でSnappy/GZIP等の圧縮や、辞書エンコーディング（Dictionary Encoding：同じ値の繰り返しをID参照に置き換える）などの高効率な符号化がかけられる

### なぜAWSでよく出てくるか: Athena/Redshift Spectrumとの相性

Parquetが試験に出やすいのは、**Amazon S3をデータレイクとして使う分析サービス（Athena、Redshift Spectrum、EMR、Glue）がスキャン量に応じて課金される**ことと直結しているため。

- Amazon Athenaは「スキャンしたデータ量（バイト数）」に対して課金される。CSV/JSONのままS3に置いてクエリすると、SELECTで使わない列も含めてファイル全体を読み切る必要がある
- Parquetに変換しておけば、クエリで参照する列のColumn Chunkだけを読めばよく、**スキャン量・実行時間・コストのいずれも大幅に削減**できる（AWSのベストプラクティスとして、CSV/JSONをGlueのETLジョブでParquetへ変換してからAthena/Redshift Spectrumでクエリする構成が定番）
- パーティショニング（例: S3のプレフィックスを`year=2026/month=08/`のように切る）と組み合わせることで、さらに読み飛ばせる範囲を広げられる

### 機械学習・GenAI文脈での用途

- SageMaker Feature Store、大規模な学習データセットの保管形式（列単位で特徴量を選んで読み出せるため、特徴量選択・EDAが高速）
- Bedrock/SageMakerのバッチ推論・前処理パイプラインで、S3上の中間データをParquetでやり取りする構成
- データレイク（S3 + Glue Data Catalog + Athena/Redshift Spectrum/EMR）における「クエリされる」前提のデータの標準的な保存形式

## ORC（Optimized Row Columnar、詳しめ）

### これは何か・なぜ生まれたか

Apache ORCは、Hadoopエコシステムの**Hive**（HadoopクラスタをSQLライクに操作するためのデータウェアハウス基盤）を高速化する目的で、Facebook社らが主導して開発した**バイナリの列指向ストレージフォーマット**。名前の通り「Row Columnar（行の集合を列指向に持つ）を最適化した」形式で、着想・目的はParquetとほぼ同じ（列単位で読み飛ばして分析クエリを高速化する）だが、生まれた出自のエコシステムが異なる。ParquetがTwitter/Cloudera（後にImpala/Spark界隈）を起点にしたのに対し、ORCはHive/Hadoop本流を起点にしている。

### 内部構造: Stripe → Column → Index

ORCの内部構造はParquetのRow Group/Column Chunkと役割はほぼ同じだが、名称と一部の仕組みが異なる。

```
ORCファイル
└─ Stripe（Parquetの Row Group に相当。デフォルトで250MB程度の大きな塊）
    ├─ Index Data（各列の統計情報・軽量インデックス。Stripe内の行を読み飛ばす判断に使う）
    ├─ Row Data（列ごとにまとめられた実データ本体）
    └─ Stripe Footer（このStripe内の各列のエンコード方式などのメタデータ）
└─ File Footer（全Stripeの位置、スキーマ、列ごとの統計情報）
└─ Postscript（圧縮方式など、ファイルを読み始めるための最小限の情報。ファイル末尾に固定長で置かれる）
```

- Parquetの「Column Chunk単位の統計情報によるプレディケートプッシュダウン」と同様に、ORCも**Stripe内をさらに細かい単位（デフォルト1万行のRow Group）に区切った軽量インデックス**を持ち、条件に合致しない範囲を読み飛ばせる
- 列ごとに合わせたエンコーディング（辞書エンコーディング、ランレングス圧縮等）と、Zlib/Snappy等の圧縮を組み合わせる点もParquetと同様の考え方

### ParquetとORCの使い分け

機能面での優劣というより、**どのクエリエンジン・エコシステムを主に使うか**で選ばれることが多い。

| 観点 | Parquet | ORC |
|---|---|---|
| 出自のエコシステム | Twitter/Cloudera（Spark/Impala系） | Facebook（Hive/Hadoop系） |
| AWSでの主な利用先 | Athena、Redshift Spectrum、EMR/Spark、Glue全般 | **EMR上のHive**、Amazon Redshift（Spectrum含む）でのネイティブサポートも厚い |
| ネストしたデータ構造への対応 | 得意（Dremel由来のネスト表現） | 対応するが、Parquetほどネスト構造の表現力を重視していない |
| 一般的な採用状況（AWSデータレイクの文脈） | **より広く使われるデフォルト的選択肢** | Hiveメタストア中心の既存Hadoop資産がある場合に選ばれやすい |

**選び方の基本方針**: どちらも「列指向・バイナリ・スキーマあり・分析クエリ最適化」という性質は共通しており、試験では機能差よりも**「CSV/JSONのようなテキスト・行指向形式と対比した、列指向バイナリ形式の代表例」**という括りで問われることが多い。新規にAWSでデータレイクを構築するなら、まずParquetを検討するのが無難（Athena/Glueのドキュメント・チュートリアルでもParquetが標準的に扱われる）。

## AWSサービスとの相性まとめ

| サービス／用途 | 相性の良いフォーマット | 理由 |
|---|---|---|
| Amazon Athena / Redshift Spectrum でのアドホック分析 | **Parquet**（ORCも可） | 列単位の読み飛ばしでスキャン量・コストを削減できる |
| AWS Glue のETL出力 | **Parquet**（CSV/JSONから変換するのが定石） | 下流の分析クエリを高速化するため |
| Amazon EMR上のHiveワークロード | **ORC**（Parquetも可） | Hiveエコシステムとの親和性が高い |
| Amazon MSK（Kafka）/ Kinesis のメッセージング | **Avro**（+ Glue Schema Registry） | スキーマ進化に強く、Producer/Consumerを独立してデプロイしやすい |
| Bedrock/SDKのリクエスト・レスポンス、設定ファイル | **JSON** | 階層構造・可読性が必要な用途 |
| SageMakerの表形式学習データ、簡易エクスポート | **CSV** | シンプルで人間が確認しやすい |

## 試験でのひっかけポイント整理

- 「Avroも列指向フォーマットである」→ 誤り。**Avroは行指向**、列指向はParquet
- 「Parquetはテキスト形式なのでエディタで直接読める」→ 誤り。**Parquetはバイナリ形式**
- 「CSVでもJSONのようなネスト構造を表現できる」→ 誤り。CSVはフラットな表形式のみ
- 「スキーマの追加・変更に強く、ストリーミング用途に向くのはParquet」→ 誤り。スキーマ進化への強さはAvroの特徴。Parquetは分析クエリの高速化が主眼で、スキーマ進化のための機構が主目的ではない
- 「Athenaのクエリコストを下げたいなら、CSV/JSONのままパーティション設計だけ工夫すればよい」→ 不十分。**フォーマット自体をParquet/ORC（列指向）に変換すること**がスキャン量削減に最も効く施策の1つ
- 「ORCは行指向フォーマットである」→ 誤り。**ORCもParquetと同じ列指向**（名前の「Row Columnar」に惑わされやすいが、行の集合＝Stripeを列指向で内部保持する形式）
- 「Parquet と ORC はどちらか一方しか列指向をサポートしない」→ 誤り。両方とも列指向バイナリ形式で、機能的な優劣というより出自のエコシステム（Spark/Impala系 vs Hive系）で使い分けられる
- 行指向＝「1件まるごと読み書き」に強い（Avro）、列指向＝「特定列の集計」に強い（Parquet／ORC）という対比で覚えると混同しにくい
