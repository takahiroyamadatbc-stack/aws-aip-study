# コンテキスト・プロンプトの問題と対処

## コンテキストウィンドウとは何か

「コンテキストウィンドウ」は**1回のFM呼び出し（1リクエスト）が同時に扱えるトークン数の上限**を指す。「モデルが会話を記憶する容量」のように誤解されやすいが、正確には以下の合計が上限に収まる必要があるという制約。

```text
コンテキストウィンドウ ≧ 入力トークン（システムプロンプト＋会話履歴＋RAGで取得したチャンク＋今回の質問） + 出力トークン（これから生成される応答）
```

- **入力トークン**: システムプロンプト、few-shot例、RAGで検索して埋め込んだチャンク、そしてマルチターン会話であればこれまでの全ターンのやり取りを含む。**FMは呼び出しをまたいで何かを覚えているわけではなく**、クライアント側（アプリケーションやBedrockのセッション管理機能）が「これまでの会話履歴」を毎回まるごと入力トークンとして再送信することで、あたかも記憶があるかのように振る舞わせている。これが「過去の会話のメモリ」の正体で、ターン数が増えるほど入力トークンは単調に増えていく
- **出力トークン**: `maxTokens`で指定する生成上限。入力側でどれだけ余裕を残していても、出力に割り当てられるトークン数が別途上限（コンテキストウィンドウ − 入力トークン、かつ`maxTokens`以下）に達すれば`stopReason: max_tokens`で打ち切られる（後述）
- **1回のセッション（マルチターン会話）とコンテキストウィンドウの関係**: セッションは複数回のFM呼び出しの連なりであり、コンテキストウィンドウは**その1回1回の呼び出し**に対する制約。セッションが長引くほど、次のターンで再送信すべき履歴が肥大化し、いずれコンテキストウィンドウを圧迫する。これが「会話を続けていたら急に入力が長すぎるエラーになった」という不具合の典型的な発生パターン

### チャンクとFM呼び出しの1対N関係

RAG（[21-rag-basics.md](21-rag-basics.md)）を組み合わせる場合、チャンクとFM呼び出しの間には以下の1対N・N対1の関係がある。

| フェーズ | 関係 | 内容 |
|---|---|---|
| Indexing（Ingestion） | 1文書 → N個のチャンク | 1つの元ドキュメントが、チャンク戦略に従って複数のチャンクに分割され、それぞれ個別にEmbedding化・格納される |
| Retrieval | 1クエリ → 上位K個のチャンク | 1回の検索で、ベクトル類似度の高い上位K件のチャンクが取得される（Kは`numberOfResults`等で指定） |
| Generation | K個のチャンク → **1回**のFM呼び出し | 取得したK個のチャンクは、個別にFMへ送られるのではなく、**すべて連結されて1回のプロンプトに埋め込まれ、1回のFM呼び出しで処理される**。「チャンクごとにFMを呼んで結果を集約する」という設計（問題44の3番目の誤答選択肢のような、文書全体を独立処理してから結果を集約するアプローチ）は、通常のRAGのRetrieveAndGenerateの動きとは異なり、文脈の断絶を招きやすい |

この1対1ではない関係を理解していないと、「チャンクを増やせば増やすほど精度が上がる」（→コンテキストウィンドウを圧迫し、無関係な情報がノイズとして混入する）といった誤った判断をしやすい。Kの大きさ（top-k）は「関連度の高い情報を十分渡す」ことと「コンテキストウィンドウ・ノイズを抑える」ことのトレードオフとして設計する。

## コンテキストウィンドウ超過・出力打ち切りへの対処

Bedrock APIの呼び出し自体は成功していても、**「入力が大きすぎる」「出力が途中で終わる」「モデルのバージョンが変わって挙動が変わった」「モデルプロバイダーごとにリクエスト/レスポンス形式が違う」**といった、コンテキストとプロンプトの取り扱いに起因する問題は別カテゴリのトラブルとして整理しておく必要がある。これらはAPIエラーとして現れることもあれば（コンテキストウィンドウオーバーフロー→400）、エラーにはならず**サイレントに品質が劣化する**形で現れることもある（出力途中終了、バージョン差異）ため、エラーコードの有無だけで問題の存在を判断できない点が実装・運用上の要注意ポイント。

## コンテキストウィンドウオーバーフロー

### 何が起きるか

モデルには最大入力トークン数（コンテキストウィンドウ）の上限があり、これを超えるリクエストは受け付けられない。会話履歴の蓄積、RAGで取得したチャンクの積み上げ、長大なシステムプロンプト、few-shot例の埋め込みなどが積み重なって上限を超えると発生する。Bedrockでは通常 **ValidationException（400）** として返る（[[51-bedrock-api-errors]]）。

### 対処法

| 対策 | 内容 |
|---|---|
| 会話履歴の要約・圧縮 | 古いターンをそのまま保持せず、要約に置き換えてトークン数を抑える（スライディングウィンドウ、要約チェーン） |
| RAG取得件数（top-k）・チャンクサイズの見直し | Knowledge Basesの検索結果を無制限に積むのではなく、関連度上位のみを渡す |
| 事前のトークン数カウント | 送信前にトークナイザーで概算し、上限に近い場合は本文を削る/要約する |
| より大きいコンテキストウィンドウのモデルへの切り替え | モデルによって上限が異なるため、要件次第でモデル選定を見直す |
| プロンプトキャッシングとの違いに注意 | Prompt Cachingは**同一プレフィックスの再処理コスト・レイテンシを削減する機能であり、コンテキストウィンドウの上限自体を拡大するものではない**（[[40-prompt-caching]]）。「キャッシュを使えば長い入力も送れる」という誤解に注意 |

## 出力が途中で切れる（レスポンスの打ち切り）

### 何が起きるか

Bedrockのレスポンスにはモデルがなぜ生成を終えたかを示す`stopReason`（Converse APIの場合）が含まれる。代表的な値は以下。

| stopReason | 意味 |
|---|---|
| `end_turn` | モデルが応答を完結させた（正常終了） |
| `max_tokens` | **`maxTokens`（出力上限）に達したため強制的に打ち切られた** |
| `stop_sequence` | 指定したストップシーケンスに到達した |
| `tool_use` | ツール呼び出しのため一旦停止（会話継続が前提） |

「出力が途中で切れる」という不具合報告の大半は`max_tokens`が原因で、エラーにはならず**200 OKで不完全な応答が返る**ため、`stopReason`を見ていないと見落としやすい。

### 対処法

- レスポンスの`stopReason`を必ずチェックし、`max_tokens`であれば打ち切りとして扱う（本文の長さだけで「完成した応答」と判断しない）
- `maxTokens`パラメータを要件に見合った値まで引き上げる（引き上げすぎはコスト増につながるため、想定される出力長から逆算する）
- 打ち切りが起きた場合、直前の応答を会話履歴に含めて「続きから生成して」と再度呼び出す継続生成パターンで補う
- クライアント側（フロントエンド、Lambdaのタイムアウトなど）で応答を途中で切っていないかも合わせて確認する（モデル側の`stopReason`が`end_turn`でも、中継経路の実装で切れることがある）

## モデルバージョン違いによる問題

### 何が起きるか

- モデルIDに明示的なバージョンを指定せず曖昧な指定（別名/最新版扱いのID）をしていると、AWS側でのモデル更新により**呼び出し側のコード変更なしに応答の傾向が変わる**ことがある
- 旧世代モデルIDが非推奨（legacy/EOL）になり、事前予告期間を過ぎると呼び出しが失敗する（[[51-bedrock-api-errors]]の ResourceNotFoundException に近い形で顕在化することもある）
- 推論プロファイル（Cross-Region Inference）を使う場合、プロファイルIDに紐づくモデルバージョンの整合性にも注意が必要（[[20-cross-region-inference]]）

### 対処法

- 本番運用では**明示的なバージョン付きモデルID**を指定し、暗黙の最新版追従に依存しない
- AWSのモデルライフサイクル通知（非推奨・EOLの案内）を監視し、移行の猶予期間内に計画的に切り替える
- モデルバージョンを切り替える際は、Bedrock Model Evaluationで新旧バージョンの応答品質を比較してから本番反映する（[[50-model-evaluation]]）
- バージョン差異はエラーを伴わないことが多いため、**定期的な品質モニタリング（自動評価ジョブや代表プロンプトでの回帰テスト）**を運用に組み込む

## スキーマ違い（モデルプロバイダー間のリクエスト/レスポンス形式差異）

### 何が起きるか

`InvokeModel`/`InvokeModelWithResponseStream`はモデルプロバイダー（Anthropic、Amazon Titan/Nova、Meta Llama、Cohere等）ごとにネイティブのリクエスト/レスポンスJSON形式が異なる。あるプロバイダー向けに書いたペイロードを別プロバイダーのモデルにそのまま送るとValidationException（400）になったり、レスポンスのパース処理がモデルを跨ぐたびに個別実装を要する。

### 対処法

- **Converse/ConverseStream API**を使い、モデル横断で統一されたリクエスト/レスポンス形式に寄せる。モデルの切り替え・比較検証（A/Bテストや評価ジョブでの複数モデル比較）を行う際にコード変更を最小化できる（[[25-streaming-responses]]）
- `InvokeModel`系を使わざるを得ない場合（Converseが未対応の機能を使う等）は、プロバイダーごとにリクエストビルダー/レスポンスパーサーを分離しておく
- モデル切り替え時は、パラメータ名の違い（例: `max_tokens_to_sample` vs `maxTokens`）や対応パラメータの有無（全モデルが同じ推論パラメータをサポートするわけではない）を個別に確認する

## 試験の勘所

- コンテキストウィンドウオーバーフローは**400番台のエラーとして顕在化する**問題、出力途中終了とバージョン差異は**エラーにならずレスポンス内容の劣化として現れる**問題という違いを区別する。後者は`stopReason`の確認や定期的な品質評価がないと気づけない
- 「Prompt Cachingを使えばコンテキストウィンドウの上限を超えられる」は誤り。キャッシュは再処理コスト・レイテンシの削減であり上限拡大ではない（[[40-prompt-caching]]）
- 出力が途中で切れる原因を「モデルの不具合」と決めつけず、まず`maxTokens`設定と`stopReason`を確認するのが定石
- モデルバージョンの暗黙追従（最新版に自動追従する指定）は、再現性・品質の一貫性を損なうリスクがあるため、本番運用では明示的なバージョン指定が推奨される
- モデルプロバイダー間のスキーマ差異は`InvokeModel`系に固有の問題であり、Converse API採用でその大部分が解消される、という関係を押さえておく
