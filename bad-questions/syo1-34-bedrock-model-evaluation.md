# syo1-34. Amazon Bedrock Model Evaluation（人間評価要素の記述不足）

## 問題文

ある企業は、Amazon Bedrock を利用して顧客からの問い合わせに対するパーソナライズされた応答を生成するカスタマーサービスアプリケーションを運用しています。
この企業は、プロンプトの有効性とモデル設定の更新ごとにそれらの品質を評価する品質保証プロセスを確立する必要があります。
このプロセスは、複数のプロンプトテンプレートから生成された応答を自動的に比較し、応答品質の問題を検知し、定量的な指標を提供し、さらに人間のレビュアーが応答に対してフィードバックを与えられる仕組みを備えていなければなりません。
また、あらかじめ定義された品質しきい値に達しない設定は、本番環境にデプロイされないようにする必要があります。
これらの要件を満たすソリューションはどれですか。

### 選択肢

**A.** AWS Lambda 関数を作成して、サンプルの顧客問い合わせを複数の Amazon Bedrock モデル設定に送信し、応答を Amazon S3 に保存します。Amazon QuickSight で応答パターンを可視化し、出力を毎日手動でレビューします。品質しきい値を満たした設定のデプロイには AWS CodePipeline を使用します。

**B.** AWS Lambda 関数を使用して自動テストフレームワークを構築し、本番トラフィックをサンプリングして更新後のモデルバージョンに重複リクエストを送信します。Amazon Comprehend のセンチメント分析で結果を比較し、センチメントスコアが低下した場合はデプロイをブロックします。

**C.（想定解答）** Amazon Bedrock の評価ジョブを使用して、カスタムプロンプトデータセットによりモデル出力を比較します。プロンプトテンプレートが変更された際に評価ジョブを実行するように AWS CodePipeline を構成します。CodePipeline は、あらかじめ定義された品質しきい値を超える設定のみをデプロイするように構成します。

**D.** Amazon CloudWatch アラームを設定して Amazon Bedrock の応答レイテンシとエラー率を監視します。Amazon EventBridge ルールでしきい値超過時にチームへ通知し、AWS Systems Manager で手動承認ワークフローを構成します。

### 解説（原文要約）

- A: 不正解。QuickSightは可視化ダッシュボードで応答品質を直接スコアリングしない。手動レビューは規模拡大で遅延・ばらつきを生み、しきい値判定の根拠データが不在。
- B: 不正解。Comprehendのセンチメント分析は感情極性のみで正確性・関連性・ハルシネーション・有害性をカバーしない。本番トラフィックのサンプリングは入力分布が制御不能で公平な比較が成立せず、**「人間レビュアーのフィードバック取り込みの仕組みも欠落している」**。
- C: 正解。Bedrockの評価ジョブは自動評価（定量メトリクス）、LLM-as-a-judge、人間評価（Likert尺度やThumbs up/down）を提供し、CodePipelineと連携してしきい値未達の設定を機械的にブロックできる。
- D: 不正解。CloudWatchのレイテンシ・エラー率は運用指標であり意味的品質を測らない。EventBridge通知やSystems Managerの手動承認は複数プロンプトテンプレートの定量比較・人間レビュアーの構造化フィードバック・自動デプロイゲートを統合しない。

## 論点

要件文は「人間のレビュアーが応答に対してフィードバックを与えられる仕組み」を、他の要件（自動比較・品質問題検知・定量指標・デプロイゲート）と並ぶ独立した必須項目として明記している。不正解選択肢Bの解説はこの要件が欠落していることを明確な失格理由として名指ししている。

ところが想定解答Cの選択肢本文は「Amazon Bedrock の評価ジョブを使用して、カスタムプロンプトデータセットによりモデル出力を比較します」としか書かれておらず、「人間評価」「レビュアーによるフィードバック」「Likert尺度」「Thumbs up/down」「ワークチーム」といった、この要件を満たすことを示す語が選択肢の文面に一切登場しない。正解の根拠が「Bedrockの評価ジョブという機能名の中に人間評価ジョブタイプが含まれる」という選択肢外の知識に依存しており、選択肢同士を文面だけで比較しても要件との対応関係が判定できない。

## 検証結果

- Amazon Bedrock Model Evaluationには「自動評価ジョブ」と「人間評価ジョブ」の2種類があり、人間評価ジョブでは自社のワークチームまたはAWS管理のワークチームがThumbs up/down・Likert尺度・比較/ランキングでレスポンスを評価できる（[Use human evaluation](https://docs.aws.amazon.com/bedrock/latest/userguide/model-evaluation-human.html)、[Evaluate the performance of Amazon Bedrock resources](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html)）。
- 選択肢Cの文面はこの「人間評価ジョブ」タイプを明示的に指定しておらず、単に「評価ジョブ」「モデル出力を比較」とだけ記述している。自動評価ジョブのみを指しているとも読める文面であり、要件の「人間のレビュアーが応答に対してフィードバックを与えられる仕組み」を満たしていることを選択肢の記述だけから確定できない。
- 一方でBの解説では同じ要件の欠落を明確に指摘しており、正解・不正解の判定基準として「人間フィードバックの有無」が使われているにもかかわらず、その基準を正解選択肢の文面上で裏付ける記述がない。

## 結論

想定解答Cが実際のAWS仕様（Bedrock評価ジョブが自動評価と人間評価の両方をカバーする）として妥当であること自体に異論はないが、選択肢の文面が「人間評価ジョブを使う」ことを明示していない点で情報量が不十分。他の不正解選択肢が「人間フィードバックの欠落」を理由に明確に排除されているのに対し、正解選択肢がその要件を満たす根拠を選択肢内に持たないのは、選択肢設計として非対称かつ言葉足らずである。出題側には「人間評価ジョブ（Likert尺度やThumbs up/down等）を構成する」のように、要件語と対応させた具体的な記述を選択肢に含めることを推奨する。
